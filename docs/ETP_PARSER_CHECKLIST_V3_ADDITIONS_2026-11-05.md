# Чек-лист 3.0 — дополнительные критерии приёмки 22 ЭТП

Дата: 05.11.2026. Статус: **предложение к чек-листу, не production acceptance**.

## Где мы сейчас и почему нужен v3

В `main` есть `docs/ETP_PARSER_STAGE_CHECKLIST.md` и 17 стадий в
`src/bankrotai/services/etp_parser_checklist.py`. Они делают лишь безопасную
пробу максимум двух страниц и 1–2 карточек. `PASS` стадии означает
**успешный ограниченный тест**, а не полностью работающий источник.

PR [#1098](https://github.com/Maximiliamos/torgi/pull/1098)
(чек-лист 2.0, не объединён) уже предлагает per-lot provenance,
`money_integrity`, `catalogue_price_coverage`, `catalogue_status_coverage`,
`detail_price_consistency`, `detail_status_consistency`,
`detail_cadastral_consistency` и `pagination_page_contract`. **Не
реализовывать их второй раз.** Сначала принять/перебазировать #1092/#1098
и координировать изменения с Draft #1086.

Этот v3-документ закрывает оставшиеся **контрактные, operational и
end-to-end пробелы**, обнаруженные при проверке НИСТП, «Торгов России»,
ЦДТ и browser-capture v7. Ниже только спецификация требуемых
проверок; добавление документа **не запускает тесты и не разрешает импорт**.

`PASS` разрешать **только при наличии указанного доказательства**, `NOT_TESTED` —
при отсутствии независимого подтверждения, `FAIL` — при противоречии, `BLOCKED` —
при запрете/ошибке доступа. `N/A` возможно лишь с source-specific пояснением.
Критическая ошибка P0 блокирует **новую source acceptance**, но не должна
отключать уже работающую основную production инфраструктуру.

## Четыре разные «готовности» — нельзя объединять в один процент

1. **D0: код/диагностика.** Зарегистрирован профиль, есть проба 1–2 страниц,
   известен первый сбой. Не доказывает даже наличие проверенного индивидуального лота.
2. **D1: приёмка источника.** Все нужные фильтры, страницы, terminal, две
   полные согласованные выборки, per-lot details, money/status/date/asset
   proof. Зелёные P0 source-гейты — только после независимого подтверждения.
3. **D2: staging → production data.** Scoped canary, DBA restore,
   idempotence, сохраняются provenance, отсутствуют неконтролируемые удаления.
4. **D3: end-to-end.** PostgreSQL + GEO + MapDataset/S3 + UI + минимум два
   успешных scheduled source cycles, на точном SHA после деплоя.

Источник получает `production_accepted=true` только после формальной
приёмки соответствующих D1–D3; отдельный D0 `PASS` никогда не даёт
такого права.

## Минимальные machine-readable артефакты каждого источника

Для каждого source ID собирать **не персональные данные**, а:
- `git_sha`, `browser_capture_sha256`, `sample_started_at_utc`,
  `scan_started_at_utc`, `scan_finished_at_utc`;
- `environment` (browser/Home/CI; VPN on/off), `request_contract`
  (метод, host/path, allowlisted ключи body/query и Content-Type,
  response status; **без реальных токенов и cookie**);
- `filter_partitions_expected`, `filter_partitions_completed`,
  `total_pages_by_partition`, `final_page_verified`,
  `scan_pass_id`, `id_set_sha256`, `records_sha256`;
- агрегаты `unique_trade_ids`, `unique_lot_ids`,
  `native_lot_ids`, `detail_verified`, `money_verified`,
  `status_verified`, `property_verified`, `geo_verified`;
- stage statuses `PASS/FAIL/BLOCKED/NOT_TESTED/N/A`, `first_failure`
  (стадия, страница, HTTP-код, категория), `last_progress_at_utc`;
- `postgres_exact_sha`, `map_dataset_version`,
  `public_ui_verified`, `two_scheduled_runs_passed`;
- защитные флаги `database_writes`, `archival_allowed`,
  `reconcile_missing`, `production_approved` с явным значением.

**Нельзя** выгружать в общий отчёт raw HTTP header/body,
личные аккаунты, cookie, session ID и другие секреты. Если сырой HTML нужен
для воспроизведения, хранить его локально в защищённом месте; в GitHub —
только обезличенные тестовые fixtures и агрегированные метрики.

## Ограничения

Таблица выше **не является фактическим отчётом** по 22 ЭТП. Это критерии
приёмки. Исторический Home sample workflow мог завершиться `success`
при **22 из 22 source-level failures/blocks**. Не перепутать успешный запуск
инструмента с успешностью каждого парсера. Последние NISTP #1093/#1103
объединены с `main`, но полный сканер #1105 ещё открыт; его локальный
Home/Windows прогон необходимо проверить отдельно.
