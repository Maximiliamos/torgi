# AGENTS.md — правила работы AI-агентов с репозиторием STERDEZ

Этот файл задаёт порядок работы для Codex и других AI-агентов, которые
поддерживают данный репозиторий. Он не заменяет проверки GitHub Actions
или ручную приёмку владельцем.

## Перед каждой задачей по ЭТП, лотам или production-импорту

**Обязательно прочитать**:
1. [Этапы диагностики ЭТП](docs/ETP_PARSER_STAGE_CHECKLIST.md).
2. [Протокол приёмки 22 ЭТП](docs/ETP_22_ACCEPTANCE_AND_LOT_VERIFICATION.md).
3. Если доступен: [Дополнительные критерии v3](docs/ETP_PARSER_CHECKLIST_V3_ADDITIONS_2026-11-05.md)
   (сейчас предложены в PR #1106; отсутствие файла в `main` не означает,
   что его можно считать принятой политикой).
4. [Исторический аудит 22 ЭТП](docs/ETP_STAGE_DIAGNOSTIC_SNAPSHOT_2026-11-05.md)
   — **не считать его текущим live-состоянием**. Проверить новые артефакты.
5. Последние open/merged PR, особенно #1092, #1094, #1097, #1098, #1099,
   Draft #1086 и текущие по соответствующему источнику. Не дублировать
   уже выполненную работу и не перезаписывать несведённые ветки.

Для задачи только по фронтенду, не затрагивающей лоты, этот блок
не требует сетевого обхода ЭТП.

## Обязательное поведение агента

1. Перед изменениями назвать **source ID**, слой (публичный каталог /
   процедура / лот / DB / GEO / карта / расписание), исходный дефект,
   подтверждённое browser/Home evidence и нужные критерии приёмки.
2. Если требуется новый сетевой контракт, зафиксировать
   **GET/POST, endpoint, Content-Type, query/body keys, schema, page/cursor,
   фильтры регионов/категорий**. Не считать `HTTP 200` доказательством
   наличия индивидуальных лотов.
3. При общем `trade_nid` идентифицировать каждый отдельный лот по
   проверенному lot number/native ID. Никогда не переносить между лотами
   кадастровый номер, цену, задаток, статус или описание.
4. Проверить первые, вторые и терминальные страницы **каждого нужного
   набора фильтров**. SSR HTML может повторять страницу 1, тогда как
   клиентская гидратация получает реальную страницу 2 через API.
5. `PASS` ограниченных 1–2 страниц не доказывает полный источник.
   Два согласованных независимых полных read-only прохода, verified
   per-lot details, фильтры, цены, статусы и отсутствие дублей нужны
   прежде, чем рекомендовать source acceptance.
6. После исправлений выполнить профильные тесты, новые отрицательные
   регрессионные тесты и соответствующий CI; зафиксировать точный SHA
   и результаты. Не называть сканирование/импорт выполненными без
   отдельных отчётов Home.
7. Перед записью в production: explicit accepted source, exact SHA,
   успешная полная приёмка, staging canary, verified backup/restore,
   защищённый импорт без разрушительной reconciliation, GEO, Map/S3/UI
   и два плановых цикла 09:00/21:00 МСК.
8. `reconcile_missing=False` и запрет массового архивирования — пока
   источник не доказал полноту и стабильность. Не обходить anti-bot,
   CAPTCHA, 403/429/503 или TLS certificate validation.
9. Если для сбора доказательств нужен российский сайт без VPN: дать
   владельцу конкретный URL и действия, использовать предоставленный
   разрешённый HTML/Network, не утверждать, что агент переключит VPN
   или продолжит работать после его отключения.
10. Не логировать и не включать в публичный PR cookies, session IDs,
    Authorization, секреты, HAR/HTML с персональными данными. Вместо
    этого прикладывать безопасные агрегаты, SHA256 и обезличенные fixtures.

## Отчёт агента после задачи по ЭТП

В комментарии к PR и итоговом сообщении указывать:

- `source_id`, точный SHA, затронутые критерии, тесты (PASS/FAIL),
  ссылки на sanitized evidence и актуальный первый блокирующий этап;
- состояния `D0 diagnostic`, `D1 source acceptance`,
  `D2 staged/production data`, `D3 end-to-end map/schedule`.
  **Нельзя объявлять D1–D3 успешными по результатам D0**;
- что осталось `NOT_TESTED`/`BLOCKED`, нужно ли владельцу открыть
  страницы без VPN;
- отдельно: были ли `database_writes`, `reconcile_missing`,
  `archival`, `geocode/map_publication` и был ли фактически выполнен
  deploy. Не выдавать `queued`/`skipped` за успех.

## Запуск текущего диагностического чек-листа (read-only)

```powershell
docker exec bankrotai-home-ingestion-worker python -m bankrotai.services.etp_parser_checklist --all --pages 2 --detail-probes 1
```

GitHub Actions: **ETP parser stage checklist (Home read-only)**.
Этот workflow зависит от успешного Home deploy или ручного запуска;
при `skipped` либо failed deploy нет нового отчёта. Даже зелёный
диагностический workflow может содержать source-level `FAIL/BLOCKED`.
Формальный источник истины — stage JSON + real source acceptance, а
не цвет общего workflow.

## Ограничения автоматизации

Это **инструкции для агента**, а не кодовый блокирующий gate.
Пока не создан отдельный required CI check и не настроена защита
ветки, невыполнение пункта само по себе не запретит merge.
